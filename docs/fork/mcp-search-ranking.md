# Ранжирование `mcp_search` в форке agentgateway: диагноз и патч

Дата: 11.10.2026. Форк: `Projects/agentgateway-fork` (Rust). Стадия: **исследование + патч в
отдельной ветке** (main не тронут, push не делался). Локальной сборки Rust нет — собирается в CI
(GitHub Actions); компиляция здесь не запускалась.

## 1. Где живёт поиск

Ленивая выдача тулов MCP — в `crates/agentgateway/src/mcp/handler.rs`:

- `LAZY_SEARCH_TOOL = "mcp_search"`, `LAZY_CALL_TOOL = "mcp_call"` — два синтетических тула,
  которые аггрегатор объявляет вместо полного каталога (`lazy_tools: true`).
- `send_lazy_search()` (`handler.rs`, ~L999) — обрабатывает вызов `mcp_search`: собирает `tools/list`
  со всех апстримов, строит каталог (`finalize_catalog`, с учётом префиксов имён и RBAC),
  ранжирует и отдаёт JSON (`render_search_matches`).
- **`search_catalog()`** (`handler.rs`, ~L241) — собственно ранжирование. Это и есть место проблемы.
- Описание тула-поиска: «Search the MCP tool catalog by name or purpose, then invoke a match with
  mcp_call»; вход — `query` (строка) и `limit` (1–25, по умолчанию 8).

Родственный, но **другой** механизм — вендорский плагин `mcp-gateway.js` (категория B, у нас
смонтирован с патчем OR-поиска, см. `harness-stack/manifest.yaml → plugins.vendor.patches`). Он
также ищет по имени/телу без морфологии, но живёт в DSH, а не в agentgateway; этот документ — про
agentgateway. Полезно помнить: там наш патч уже заменил совпадение **всех** слов (AND) на OR —
ровно потому, что фразовые/русские запросы ничего не находили.

## 2. Диагноз

Исходный `search_catalog`:

```rust
let tokens: Vec<String> = query
    .to_lowercase()
    .split(|c: char| !(c.is_alphanumeric() || c == '_' || c == '-'))   // токены по словам
    .filter(|t| !t.is_empty())
    .map(|t| t.to_string())
    .collect();
...
for tok in &tokens {
    if name.contains(tok.as_str()) { score += 10; }   // имя тула
    if desc.contains(tok.as_str()) { score += 2; }    // описание
}
```

Проблема: после разбиения на токены матч идёт через **`str::contains`** — точную подстроку.
Токенизация и `to_lowercase` для кириллицы работают корректно (`char::is_alphanumeric` включает
кириллицу, `to_lowercase` — Unicode-aware). Ломается **сопоставление форм слова**: у русского
слова падеж/число меняет окончание, и одна форма не является подстрокой другой, поэтому тул,
найденный в описании в другой форме, теряется.

| Запрос | Слово в описании | `desc.contains(токен)` | Итог |
|---|---|---|---|
| «решения» | «решение» | `"…решение…".contains("решения")` → false | ❌ мимо |
| «памяти» | «память» | false | ❌ мимо |
| «доска» | «на доске» | false | ❌ мимо |
| «решения» | «решениями» | `contains("решения")` → true | ✅ (повезло) |
| «status» | «status» | true | ✅ (латиница) |

То есть **recall** (полнота) страдает на любой морфологической форме, кроме случайно совпадающей
подстроки; латиница и имена тулов (`project_status`, `db_inspect`) не затронуты, потому что у них
морфологии нет.

## 3. Патч

Ветка форка: **`feat/mcp-search-morphology`** (от `pr/mcp-lazy-tools`), коммит `1aa55a3c`, файл
`crates/agentgateway/src/mcp/handler.rs`. Push не делался.

Идея: **не менять точное поведение для латиницы** (имена тулов, английские описания — как было),
а для **кириллических** токенов добавить терпимость к окончаниям: токен и слово описания
сопоставляются, если у них общий префикс, покрывающий слово-из-двух почти целиком — расхождение не
более двух последних символов у более короткого.

Добавлены три функции:

- `split_words(text) -> Vec<&str>` — разбиение описания на слова теми же разделителями, что и запрос;
- `is_cyrillic(c)` — диапазон U+0400–U+04FF;
- `inflect_match(token, word)` — ядро: если в токене нет кириллицы → `false` (латиница идёт точным
  путём); иначе `common >= 3 && common + 2 >= shorter`, где `common` — длина общего префикса,
  `shorter` — длина более короткого из двух.

И изменён один блок в `search_catalog`: к проверке `desc.contains(tok)` добавлено
`|| desc_words.iter().any(|w| inflect_match(tok, w))`.

```diff
@@ fn search_catalog
 			let name = t.name.to_lowercase();
 			let desc = t.description.as_deref().unwrap_or("").to_lowercase();
+			let desc_words = split_words(&desc);
 			let mut score = 0i64;
 			for tok in &tokens {
 				if name.contains(tok.as_str()) {
 					score += 10;
 				}
-				if desc.contains(tok.as_str()) {
+				if desc.contains(tok.as_str()) || desc_words.iter().any(|w| inflect_match(tok, w)) {
 					score += 2;
 				}
 			}
```

Порог `common >= 3` не даёт срабатывать односимвольным токенам («и», «в») и слишком коротким
основам; `common + 2 >= shorter` разрешает ровно ту разницу окончаний, что нужна для типовых форм
(1–2 символа), но не «склеивает» слова с разными корнями.

## 4. Влияние на кириллицу

Что теперь находит (проверяется тестом `search_catalog_matches_inflected_cyrillic`):

- «решения»/«решению» → описание «Читает **решение** по проекту» (общий префикс «решени» = 6);
- «доска» → описание «Список задач на **доске**» («доск» = 4);
- «памяти» → описание «Краткая **память** агента» («памят» = 5).

Что не изменилось:

- латиница — прежний точный `contains` (`inflect_match` возвращает `false` для ASCII-токенов);
- веса: имя тула +10, описание +2, сортировка по убыванию score, затем по имени; пустой запрос —
  пустой результат;
- `limit` и формат ответа (`render_search_matches`) не тронуты.

## 5. Риски и тюнинг

- **Ложные срабатывания.** Префиксная терпимость может свести близкие слова: «память»/«памятник»,
  «статус»/«статья». Для поиска тулов это приемлемо (лишний кандидат в выдаче, не ошибка), но если
  шум мешает — поднять порог (`common >= 4`) или требовать `common == shorter` для коротких слов.
- **Изменение семантики допускается только для кириллицы** — риск регрессий по английским запросам
  исключён ветвлением по `is_cyrillic`.
- **Не полный stemmer.** Это эвристика, а не Snowball-Russian: редкие/нерегулярные формы могут
  остаться вне выдачи. Если полнота критична — следующий шаг: лёгкий стеммер (Porter-lite) для
  кириллицы + сравнение стемов, плюс возможно расширение `mcp_search` на «теги/синонимы» из описаний.
- **Стоимость.** `split_words` вызывается один раз на тул (не на токен); каталог — сотни тулов,
  запрос короткий — влияние на латентность пренебрежимо.

## 6. Тест

Добавлен в `mod tests` (`handler.rs`): `search_catalog_matches_inflected_cyrillic` — четыре
позитивные проверки (разные формы) и три негативные (чужие тулы не попадают; латиница работает по
точному совпадению). Каталог строится заново на каждый вызов, поэтому тест не зависит от `Tool: Clone`.

Существующий тест `search_catalog_ranks_name_hits_above_description` (латиница: `status`,
`project_status`, `db_inspect`) сохранён без изменений и должен проходить — регрессии по английскому
пути не ожидается.
